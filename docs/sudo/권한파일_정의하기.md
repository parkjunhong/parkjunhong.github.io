# 권한파일의 단일화? 다중화? 

`/etc/sudoers.d/` 디렉토리를 활용할 때 **"단일 사용자당 하나의 파일로 병합(Merge)할 것인가"** 아니면 "기능이나 스크립트 단위로 새로운 파일을 분리(Drop-in)할 것인가"는 시스템 관리자와 인프라 아키텍트들이 실제로 많이 고민하는 아주 훌륭한 주제입니다.

결론부터 말씀드리면, **절대적으로 옳은 하나의 정답은 없으며 관리 목적에 따라 합리적인 선택이 달라집니다.** 두 가지 접근 방식을 주요 기준에 따라 비교 검토해 드리겠습니다.

---

### 1. 계정명과 동일한 단일 파일 유지 (1 User = 1 File, 병합 방식)

사용자 계정명으로 단일 파일을 만들고, 새로운 명령어가 필요할 때마다 해당 파일의 내용을 파싱하여 병합(Merge)하는 방식입니다. (우리가 앞서 작성한 스크립트의 동작 방식입니다.)

* **장점:**
* **가독성 및 직관성:** 시스템 관리자가 특정 사용자(`ymtech`)가 어떤 권한을 가지고 있는지 확인하고 싶을 때, 파일 하나만 열어보면 전체 권한을 한눈에 파악할 수 있습니다.
* **파일 파편화 방지:** 디렉토리 내에 수십 개의 자잘한 파일이 생성되는 것을 막아, 디렉토리가 깔끔하게 유지됩니다.


* **단점:**
* **파싱 및 병합의 복잡성:** 코드로 자동화할 때 기존 파일을 읽고, 콤마를 분리하고, 중복을 제거하고, 다시 쓰는 복잡한 로직이 필요합니다. 스크립트에 버그가 있을 경우 파일 전체가 망가질 위험(Risk)이 있습니다.
* **목적 추적의 어려움:** 파일 안에 `cat`, `systemctl`, `tar` 등 다양한 명령어가 섞이게 되는데, 각 명령어가 어떤 목적(예: 백업용인지, 모니터링용인지)으로 추가되었는지 나중에는 알기 어렵습니다.



### 2. 목적/기능별 새로운 파일 생성 (Drop-in 파일 방식)

사용자 기준이 아니라 부여하려는 '기능'이나 '역할'을 기준으로 파일을 분리하는 방식입니다. (예: `10-ymtech-monitoring`, `20-ymtech-backup`)

* **장점:**
* **완벽한 원자성(Atomicity)과 롤백:** 특정 기능(예: 백업)에 대한 권한을 회수하고 싶다면, 파일을 수정할 필요 없이 `rm 20-ymtech-backup` 명령어 하나로 깔끔하고 안전하게 롤백됩니다.
* **안전한 자동화 (멱등성):** 기존 파일을 읽고 파싱할 필요가 없습니다. 설정 템플릿을 그대로 덮어쓰기만 하면 되므로 쉘 스크립트나 Ansible, Chef 같은 자동화 도구를 사용하기에 훨씬 적합한 현대적인 IaC(Infrastructure as Code) 방식입니다.
* **주석 및 목적의 명확화:** 파일명 자체가 목적을 나타내므로 관리가 용이합니다.


* **단점:**
* **우선순위(순서) 관리의 필요성:** `sudoers`는 파일의 이름을 알파벳/숫자 순서로 읽으며, 나중에 읽힌 파일이 이전 설정을 덮어씁니다. 파일명이 꼬이면 의도치 않게 권한이 축소되거나 확장될 수 있습니다.
* **권한 파악의 파편화:** 특정 사용자의 전체 권한을 보려면 관련된 여러 파일을 모두 뒤져보거나 `sudo -l -U ymtech` 명령어로 최종 결과만을 확인해야 합니다.



---

### 3. 종합 비교 요약

| 검토 기준 | 1 User = 1 File (병합 방식) | 기능/목적별 파일 분리 (Drop-in 방식) |
| --- | --- | --- |
| **관리의 기준점** | '사용자' 중심 | '기능 및 역할' 중심 |
| **스크립트 복잡도** | 높음 (파싱, 중복제거, 덮어쓰기 필요) | 낮음 (단순 파일 생성 및 삭제) |
| **롤백(권한 회수) 용이성** | 낮음 (파일을 열어 특정 문자열만 찾아 지워야 함) | 매우 높음 (해당 파일만 삭제하면 끝) |
| **사용자 권한 가독성** | 매우 높음 (파일 하나에 모두 정리됨) | 낮음 (여러 파일에 분산됨) |
| **현대적 인프라 표준** | 소규모 또는 수동 관리에 적합 | 대규모 클라우드 및 자동화 배포에 적합 |

---

### 💡 전문가 제언

만약 이 스크립트를 "소수의 개발자나 엔지니어에게 일상적인 유지보수 권한을 부여하는 툴"로 사용하신다면, 직관적으로 계정명과 1:1로 매칭되는 **병합(Merge) 방식이 더 합리적**입니다.

반면, 이 스크립트가 "특정 애플리케이션(예: 모니터링 에이전트, 백업 솔루션)을 설치할 때 필요한 권한을 시스템에 주입하기 위한 배포 스크립트"라면, 병합 방식보다는 **기능별로 파일을 뚝뚝 떨어뜨려 놓는 분리 생성 방식이 훨씬 안전하고 합리적**입니다.


# 사내 시스템에 대한 '전사적 권한 설정 및 관리'

인프라 보안과 운영 효율성 측면에서 매우 중요한 단계에 진입하셨습니다.

전사적 관리라는 명확한 목표가 있다면, 앞서 논의했던 기준들을 엔터프라이즈(Enterprise) 인프라 관리 관점에서 다시 평가해 볼 필요가 있습니다.

---

### 전사적 권한 관리 관점에서의 아키텍처 평가

현재 작성된 스크립트는 **'개별 사용자(User) 1명 = 1개의 파일 병합'** 방식을 취하고 있습니다. 이 방식이 전사적 환경에 적용될 때의 현실적인 장단점은 다음과 같습니다.

**1. 현재 방식의 한계점 (사용자 중심 관리)**

* **운영 오버헤드 증가:** 만약 50명의 개발자에게 동일한 `systemctl` 권한을 주어야 한다면, 스크립트를 50번 실행하거나 반복문(loop)을 만들어야 합니다.
* **부서 이동 및 퇴사자 관리의 어려움:** 직원의 부서가 변경되어 권한을 회수해야 할 때, 병합된 파일 내부에서 특정 명령어만 골라내어 삭제하는 과정이 매우 까다롭습니다.

**2. 엔터프라이즈 글로벌 표준 (역할 및 그룹 중심 관리 - Role-Based Access Control)**

* 전사적 관리를 수행하는 대부분의 기업은 개별 사용자(`user`)가 아닌 시스템 그룹(`%group`)을 기준으로 권한을 부여합니다.
* 예를 들어, DBA 그룹(`%dba`), 웹 개발자 그룹(`%webdev`), 모니터링 그룹(`%monitor`) 등을 만들고, 권한 파일은 `/etc/sudoers.d/role_dba`와 같이 **기능별(Drop-in)로 분리**하여 생성합니다.
* **장점:** 권한 제어가 필요할 때 `sudoers` 파일을 수정할 필요 없이, 해당 직원을 리눅스 그룹에 추가(Add)하거나 제거(Remove)하는 것만으로 완벽하게 통제됩니다.

---

### 💡 전문가 제언

목적을 고려했을 때, 현재 작성된 스크립트의 **'명령어 자동 검증 및 설치' 기능은 매우 훌륭한 자동화 도구**입니다. 하지만 타겟을 '개별 사용자'로만 한정 짓기에는 전사적 확장성이 조금 아쉽습니다.

**최종 권고 방향:**
현재 스크립트의 훌륭한 로직(검증, 설치, 병합)은 그대로 유지하되, 타겟 대상을 개별 사용자(`-u`)뿐만 아니라 시스템 그룹(`-g`)으로도 지정할 수 있도록 유연성을 더하는 것을 강력히 권장합니다.  

이렇게 하면 전사적 표준 권한은 그룹 단위로 배포하고, 예외적인 권한만 개별 사용자 단위로 관리하는 이상적인 하이브리드 환경을 구축하실 수 있습니다.
